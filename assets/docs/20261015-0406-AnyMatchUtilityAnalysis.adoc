== Summary

Every `jdkList.stream().anyMatch(...)` call leaves 6 to 7 objects (160 to 176 bytes) behind for the garbage collector. `Iterate.anySatisfy` and `Iterate.anySatisfyWith` on the same `java.util.List` leave none: 0 bytes per call at every match position, 0 GC runs. At 10 million calls per second the stream version alone allocates about 1.6 to 1.8 GB/s, which is the heap headroom an application has to keep in reserve for a traffic spike; the EC versions need none. EC is also several times faster here (see the table), but the memory difference is the point: it is constant per call, so it grows linearly with load.

== Garbage: where it comes from

*Pipeline garbage (JDK only, measured).* Each `stream().anyMatch()` call builds a `ReferencePipeline$Head` (48 B), an `AbstractList$RandomAccessSpliterator` (32 B), a `MatchOps$MatchOp` (24 B), a `MatchOps$1MatchSink` (24 B) and a `MatchOps` lambda (16 B). These are pipeline plumbing and exist no matter what lambda you pass.

*Lambda garbage (measured).* On top of that the JDK call allocates the captured method reference `Integer.valueOf(this.test)::equals` (16 B) and, for `test = 500` and `1000`, the `Integer` box (16 B; values outside -128..127 are not cached). Escape analysis cannot remove them because they escape into the pipeline objects. In the EC calls the same capturing lambda never escapes `Iterate.anySatisfy`, so escape analysis removes it and the histogram shows nothing.

With escape analysis off, the lambda shape becomes visible. `ecAnySatisfy` (capturing) allocates 16 B at `test = 1` (the lambda) and 32 B at `test = 500/1000` (lambda plus `Integer` box). `ecAnySatisfyWith` (fat-free) allocates 0 B at `test = 1` and 16 B at `test = 500/1000`: only the `Integer` box from autoboxing `this.test`, an `int`, into the `Object` parameter. So the fat-free form halves the garbage, and removes it entirely when the parameter is already an object. The JDK stream allocates the same 160 to 176 B with or without escape analysis: its garbage does not depend on the JIT at all.

== Spikes and heap headroom (derived, not measured)

JMH also reports `gc.alloc.rate` (MB/s), but that number scales with how fast the benchmark runs, so a faster method can show a higher MB/s while allocating the same per call. `gc.alloc.rate.norm` (bytes per call) is the number to size heaps with.

The derived numbers above use the measured bytes per call. They assume every call allocates the same amount, which the histograms confirm (exactly 1.00 of each object per call).

Bytes per call here are `gc.alloc.rate.norm` from the main runs. Where that is a few bytes below the object-count total, the JIT scalar-replaced one pipeline object in some forks; the object-count run (exact per-class counts) is the reference for what each call allocates.

Compact headers shrink the JDK stream's garbage from 176 to 160 B (test = 1) and 192 to 176 B (test = 500, and in the histogram at 1000), about 9%. Object counts do not change. Only objects whose size crosses an 8-byte boundary get smaller (`ReferencePipeline$Head` 56 to 48 B, the `MatchOps` lambda 24 to 16 B). The best fix is still to not allocate: compact headers save 16 B per call, the fat-free EC call saves all 160 to 176 B.

Unexpected, measured: on this machine the EC loops ran about 15 to 20% *faster* with compact headers off (for example `ecAnySatisfy` at `test = 1000`). *Inferred:* `Integer.equals` checks the class of every element, and with compact headers the class pointer has to be decoded from the header word. Check this on the Mac before quoting it.

== Supporting analysis

*Fixed vs per-element cost.* EC: about 2.3 ns at `test = 1` and about 0.65 ns per element scanned (`test = 1000`). JDK: about 30 ns fixed cost to build and tear down the pipeline, plus about 3.0 ns per element at `test = 1000`, so the JDK is slower per element too, not only at setup.

*Rerun.* The first `coh-on` run of this class overlapped with a short chart-rendering test on the same machine, so it was rerun on its own after the full run; the analysis uses the rerun. The overlapped files are kept as `AnyMatchUtility-coh-on.overlapped.*`.

== Caveats
