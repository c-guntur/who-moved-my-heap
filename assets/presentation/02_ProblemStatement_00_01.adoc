== The problem in one slide

[.lead]
JDK collections and streams spend heap on objects the code never mentions.

* Boxed `Integer`s and per-entry nodes inflate what a collection holds.
* Every stream call builds a pipeline of objects and drops it.
* How much garbage depends on the JIT, the `Integer` cache and the headers.
* Fat-free (non-capturing) lambdas and plain loops leave far less behind.

[.notes]
--
Every number in this series comes from two runs on JDK 25.0.4.1 in the cloud sandbox:
movers `20261015-1503` (JOL footprints, compact object headers off and on) and
shakers `20261015-0406` (JMH bytes per call, GC counts and class-histogram object counts).
The point is footprint and headroom for spikes, not only throughput.
--
